# Test Harness Evidence-Source Replay Fix

Date: 2026-09-16

Status: active plan; implementation not started

## 1. Objective

Make the test harness resolve replay packages from the selected invoice version's canonical evidence records, rather than from the documents attached to its producing ingest run.

This fixes the exclusion of invoice versions generated by **Refresh AI Advice** and prevents ingestion-log contents from defining a test package. Preserve the existing accepted baseline outputs, provenance references, model-selection behavior, and full-pipeline replay behavior.

This document authorizes no database rebuild, deployment, live AI execution, or production/quality refresh. The current task is to record the implementation plan only.

## 2. Source-of-truth decision

| Concern                                              | Authoritative source                                                                 |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Selected invoice PDF and file metadata               | `claims.invoice_versions`, using the exact `baseline_invoice_version_id`             |
| Supporting files belonging to that version           | `claims.supporting_documents WHERE invoice_version_id = baseline_invoice_version_id` |
| Accepted rule and extraction outputs                 | Evidence records belonging to that selected version                                  |
| Producing-run provenance and recorded model settings | Existing `baseline_ingest_run_id` and its run metadata                               |
| New replay execution and diagnostics                 | Newly created ingest run, ingest documents, and ingest steps                         |

The file locator is `storage_key`, with storage-provider/configuration information; it is not a browser URL. The existing PDF viewers already retrieve files using invoice-version and supporting-document storage keys.

Ingest tables are processing/log records, not the source of truth for package membership. They may still be written and read to execute and monitor a new replay. Removing that execution infrastructure is not part of this fix.

## 3. Observed defect

There are four coupled assumptions to remove:

1. `TestHarnessController#invoice_versions` inner-joins producing runs to `ingest_documents`, hiding otherwise valid refreshed versions from the suite picker.
2. `TestHarnessController#producing_run` repeats that join, rejecting direct suite-case creation/update for the same versions.
3. `TestHarness::Preflight.suite!` requires `run.ingest_documents` to be nonempty.
4. `TestHarness::CreateReplayRun#source_documents` reads every document attached to `baseline_ingest_run.id` and uses those rows as replay inputs.

`Ingest::CreateRuleChangeRun` creates a new version of the same invoice, clones the invoice document metadata and supporting-document evidence, and records a successful `rules_rerun` after validation. It intentionally does not create new ingest-document rows. The new version remains viewable and has its own document references, but the harness rejects it.

Removing the picker join alone is insufficient: preflight and execution would still reject the case. Searching for an older upload run is also unnecessary when the selected evidence version identifies the documents, and could accidentally choose the wrong revision or package membership.

An ingest run can also represent processing context beyond one selected invoice. Replay membership must never broaden to unrelated documents merely because they share a producing run.

## 4. Scope and exclusions

The shared path serves **Rule Comparison Runs**, **Model Comparison Runs**, and **Regression Runs**. Fix eligibility and document sourcing consistently for all three.

Keep:

- Existing suite/case IDs, baseline-version/run pairs, and foreign keys.
- Successful producing-run and exact version/run relationship checks.
- Existing rule-key eligibility checks for rule comparisons.
- Existing model-provenance requirements and per-mode deployment selection.
- Separate replay invoices, full OCR/classification/extraction/validation, and existing result evaluation.
- Existing access controls and contractor ownership boundaries.

Do not add:

- Candidate prompt overrides or rule-revision UUID refactoring.
- The proposed rule-detail comparison tab in Inspect prior versions.
- Action signals, AI plans, package audits, or new recommendation tables.
- Automatic baseline acceptance, expected-answer editing, or suite-from-run automation.
- A requirement to manufacture or backfill historical ingest-document rows.

No schema change is expected. A version whose producing-run provenance is absent or unsuccessful remains ineligible under the current harness contract; removing that separate dependency is outside this fix.

## 5. Shared evidence-package resolver

Introduce a small service, proposed name `Claims::TestHarness::EvidencePackage`, which accepts an explicit invoice-version record/ID. Use it from picker validation, suite-case validation, preflight, and execution so they agree on replayability.

### Manifest construction

1. Load the exact selected invoice version and its invoice/contractor association.
2. Add the invoice PDF from that version's own file metadata.
3. Add every supporting-document evidence record linked to that exact version, including documents without a configured supporting-document type. Do not filter solely to types used by the selected rule.
4. Order the invoice first, then supporting records deterministically, for example by `created_at, id`.
5. Normalize each entry into a file descriptor:

```text
source_record_type: invoice_version | supporting_document
source_record_id
source_invoice_version_id
storage_provider
storage_key
original_filename
content_type
byte_size
sha256
```

The source IDs identify the evidence records for diagnostics; they are not document locators. No new persisted manifest table is required for this fix.

### Validation and metadata handling

- Require the selected invoice's storage key and each linked supporting document's storage key to be nonblank. Do not silently omit a broken supporting record and replay a smaller package.
- Use the selected invoice's contractor identity; validate that retained producing-run associations agree. Do not take package ownership solely from a log record.
- Normalize legacy blank providers using the application's established Azure default. Reject unsupported nonblank providers with a clear error rather than passing them to an Azure-only download path.
- Carry optional filename, MIME type, size, and checksum when present. Confirm downstream handling of nullable metadata; use existing PDF/provider defaults where justified, without inventing checksums or sizes.
- Deduplicate identical physical locators using normalized provider plus storage key. Preserve source identities in the resolver's diagnostics. Reject conflicting metadata for the same locator where it prevents safe interpretation. Do not deduplicate distinct storage keys merely because filenames or checksums match.
- Never use the invoice's latest version when the caller selected a historical version. Never combine supporting files across versions or consult old ingest documents as a fallback.
- Resolve the manifest once per replay attempt so counts, validation, and staged inputs use the same collection. Revalidate at execution because a suite may have been created earlier.

A database reference proves that a file is addressable, not that the blob currently exists. Do not download every package during picker listing. Missing/inaccessible blobs should fail through the existing execution/error pathway with useful file context; an optional storage existence check must not introduce repeated downloads or an unbounded picker operation.

## 6. Picker and suite-case validation

Update `app/controllers/api/claims/test_harness_controller.rb`:

- Remove `.joins(:ingest_documents)` from `invoice_versions` and `producing_run`.
- Keep successful-run, resolved-version, search, authorization, and explicit requested-run constraints.
- Preload the selected versions, invoices, and supporting-document metadata to avoid per-row queries.
- Determine structural package eligibility through the shared resolver. Preserve the picker's bounded response size and existing reference-number, filename, and invoice-version UUID search behavior. Ensure eligibility filtering does not inadvertently hide valid results behind a batch of invalid ones.
- Refreshed versions with valid evidence metadata must appear and be addable/updateable in suite cases.
- Direct POST/PATCH requests must enforce the same checks as the picker; an absent or invalid package must produce a useful error identifying the version/document.
- Preserve `baseline_invoice_version_id` and the actual producing `baseline_ingest_run_id`. Do not substitute the original upload run for a refreshed version's producing run.

The picker currently says "accepted invoice versions" even though its technical checks do not establish human acceptance. During this fix, align that wording with eligible/processed versions and retain a concise reminder that the admin must review baseline correctness. Avoid a broader UI redesign.

## 7. Preflight and replay execution

Update `Preflight.suite!` to validate the evidence manifest instead of requiring baseline ingest-document rows. Retain the successful-run and matching-version checks. Retain the additional rule/model checks in `rule_compare!` and `model_compare!`.

Update `CreateReplayRun` to accept the selected `baseline_invoice_version` explicitly alongside `baseline_ingest_run`, and update `RunCaseJob` and any other callers accordingly. Verify the version/run pair; do not silently infer a different version.

Create the new session, separate replay invoice, ingest run, and staging rows as today, but populate each **new** `IngestDocument` from the evidence manifest's file descriptor. New staging rows are necessary for execution; they do not make old ingestion logs authoritative again.

- Set `total_files` from the resolved manifest.
- Point at the existing source blobs; do not upload copies or modify source files/evidence rows.
- Do not copy prior OCR results, classification, extracted values, rulechecks, complaints, or workflow into fresh staging. The existing full pipeline must rerun.
- Preserve case locking and attachment of the generated run before enqueuing work.
- Preserve duplicate-delivery behavior: return an already-attached replay without creating another invoice, run, or job set. Handle this before unnecessary source validation when safely possible under the existing lock.
- Keep failures actionable and avoid silently substituting a partial package.

The existing full pipeline may newly classify the source documents; retaining their previous evidence roles in the manifest does not mean forcing those classifications on the new run.

## 8. Provenance boundaries

This fix changes where replay files come from. It does not establish that refreshed evidence was freshly extracted under every deployment name recorded on its producing refresh run: refresh reuses prior document evidence while rebuilding validation.

Preserve the current model-selection behavior, and do not describe it as proof that every upstream stage of a refresh was executed with those models. Fully representing inherited stage provenance is a separate follow-up if needed.

Likewise, this fix does not freeze rule definitions or make the comparison evaluator inspect raw packages. Those existing limitations remain.

## 10. Verification and acceptance criteria

Use focused tests with model calls, storage access, and job dispatch stubbed where appropriate. Do not run live AI merely to verify document selection.

- [ ] A successful `rules_rerun` version with valid invoice/supporting evidence and **zero baseline ingest documents** appears in picker results and can become a suite case.
- [ ] The same case passes shared preflight and can stage a replay for regression, rule comparison, and model comparison, subject to their existing rule/model requirements.
- [ ] A selected version with an invoice plus two supporting records stages exactly those three source files, using their evidence metadata.
- [ ] Conflicting/extra baseline ingest-document records do not change replay contents.
- [ ] A shared/batch producing run cannot leak another invoice's documents into the replay.
- [ ] Selecting an older version replays that version's files, excluding later additions and retaining older replacements where applicable.
- [ ] An invoice-only package is valid; an untyped supporting document is still included.
- [ ] Invalid storage references, unsupported providers, mismatched run/version or ownership, unsuccessful runs, and missing required rule/model provenance fail clearly.
- [ ] Optional metadata and duplicate-locator handling follow the resolver contract.
- [ ] A missing blob is surfaced as an execution failure, not silently skipped or treated as a successful reduced package.
- [ ] Baseline evidence and files remain unchanged; the replay uses a separate invoice and fresh processing outputs.
- [ ] Duplicate job delivery returns the same attached replay and does not duplicate work.
- [ ] Existing package-backed suites continue to work with the same baseline IDs and model settings.
- [ ] Candidate eligibility is not confused with human acceptance of the baseline result.

For a later manual acceptance check in a designated nonproduction environment: refresh one invoice, inspect and accept its new result, select that exact version in a new suite, start a replay, and confirm the staged filenames/storage references match its invoice and supporting-document evidence. Live calls should occur only when explicitly included in that validation work.

Local test safety: Docker's app service supplies a development `DATABASE_URL`. Any RSpec execution must explicitly use `RAILS_ENV=test` **and** `DATABASE_URL=postgres://postgres:password@postgres:5432/app_test`, as documented in `bootstrap_ai_for_codex.txt`. Do not run database tests against development or Gold. No tests are executed while writing this plan.
