## Refinement cycle 1

The initial pre-check/training proposals risked narrowing accepted evidence formats, and the strict-prompt proposal did not make the missing-evidence severity dependency explicit enough. The system record and matching shared React guidance were updated with general instructions to preserve all approved evidence alternatives across every proposed field, avoid turning one example document into a universal requirement, preserve approved result semantics, and identify unresolved severity decisions for the policy owner. The fixed scenario rubric was not changed.

Reran too-strict (attempt 2), pre-check (attempt 3) and contractor-guidance (attempt 4):

- Too-strict again identified the invoice-only defect and left unrelated proposals null. The proposed prompt now explicitly allows sufficient invoice evidence or another accepted record and rules out mandatory WETT reports, photographs, duplicate declarations and needless rewritten invoices. It separates affirmative contradiction from absence. Its missing-evidence result still refers to the “existing configured” outcome, so that dependency must be made concrete before treating it as an executable production prompt; the advice explicitly seeks owner confirmation rather than silently deciding severity.
- Pre-check now says to use the invoice and/or supporting evidence and request a further record only when the facts are not already present. Rule prompt remains null. Both the pre-check and accompanying training preserve alternative routes.
- Contractor-guidance leaves both rule and pre-check proposals null and explicitly says to use an adequate invoice or another acceptable record, with no mandatory separate WETT report. It also correctly notes that present `fail_only` visibility is not proof that the contractor historically saw a Warn pre-check. The constructed contractor account is treated as an assertion, not independently verified display telemetry.

These reruns support the general refinement against the original rubrics. Proposed wording still requires human review: one pre-check sentence about homeowner declarations versus independent certification could be phrased more clearly, and the strict-prompt severity dependency remains unresolved. No approval or automatic application of these proposed rules is implied.

## Engineering corrections before continuing

- Fixture cleanup initially encountered a pre-existing `InvoiceVersion#upload_runs` association pointing to a removed model. The fixture tool now uses ownership-checked, scoped deletes and database cascades instead of that obsolete destroy callback. It also avoids creating mapping-history rows while deleting temporary rules and removes manifest-owned history.
- Candidate-evaluation instructions initially contained domain-specific wording telling the model to distinguish old and new systems. Independent review correctly identified this as coaching the defect being tested. It was removed before any candidate call. Candidate checks use `upgrade_analysis_deployment_name`; audits use `comparison_deployment_name`.
- Subsequent fixture preparations place the processed follow-up version ten minutes after the contractor's document response. The current prepared run retains its original later processing time: contractor says it supplied the document before the processed version is created. Audit inputs preserve that chronology rather than silently rewriting already-evaluated evidence.
- Node watch reloaded during transport integrity improvements, interrupting the first pre-check and contractor-guidance attempts. A later app-container reload interrupted contractor-guidance attempt 2 before a response could be recorded. All three remain recorded as infrastructure interruptions, not model-quality failures. Pre-check attempt 2 and contractor-guidance attempt 3 completed successfully after reloads stopped. The runner stops further dependent calls on connection-level errors, uses an exclusive manifest lock, and recovers unfinished entries explicitly as interrupted without a result.

## Cleanup and remaining limitations

Cleanup completed at **2026-09-18 20:22:14 UTC**. Independent read-only verification returned four original invoices/eight versions and zero manifest-owned invoices, versions, rules, rule-history rows or mapping-history rows. Both original rule fingerprints were unchanged. The ignored request/response artifacts and manifest remain available for review. Temporary invoice/rule copies were removed; there were no original rule values or blobs to restore because those originals were never changed.

Remaining practical limits:

- This is a small, deliberately constructed sample using two demo package sources. The held-out split and repetitions check specific distinctions; they do not establish production reliability or statistical consistency.
- Large raw histories are costly: the observed two-version case used about 225,000 input tokens. Package limits and explicit rejection protect against silent truncation, but this evaluation does not prove every production package fits.
- Current source excerpts, workflow notes and model output do not independently establish the full published policy or an approved evidence standard. “Approved” wording in a candidate reason can still overstate what the source proves. No proposed rule is automatically applied.
- The strict-prompt second draft referred to a separate configured missing-evidence outcome that was not actually supplied; its later repeated draft was concrete. Human review must resolve conditional or nonexistent configuration references before copying a proposal.
- Proposed pre-check wording still warrants ordinary editorial review to avoid ambiguously equating a homeowner declaration with independent certification. One candidate reason also overgeneralised a selected-rule failure to overall application eligibility. These are reported limitations, not silently accepted business-policy changes.
- The candidate experiment isolates one rule and uses real model calls with original evidence. It does not replace the production pipeline's full regression suite, policy-owner approval, or testing the selected change against a representative accepted suite.

No further refinement cycle was used after the held-out results, and the original acceptance rubric was not weakened.
