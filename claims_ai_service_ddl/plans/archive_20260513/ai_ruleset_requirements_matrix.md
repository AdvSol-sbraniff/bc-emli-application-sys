# AI Ruleset Requirements Matrix

Purpose: working matrix for translating Better Homes BC Energy Savings Program requirements into traceable validation rules.

Source:

- Better Homes BC, `Energy Savings Program requirements`
- Public URL: https://betterhomesbc.ca/learn-about-programs/energy-savings-program/energy-savings-program-requirements/
- PDF/source snapshot linked by the public page: `Rebate Eligibility Requirements - Energy Savings Program`
- Source effective date: invoices dated on or after April 1, 2026
- Created/expanded by Codex: May 2026

This is not final program policy. It is the analysis layer between public guidance and executable AI/code rules.

Source anchors are working references from the current public page/PDF snapshot. They should be rechecked before a production ruleset is published.

## Matrix Method

Each row represents a rule candidate or rule group.

Rules are deliberately classified by evaluator:

- `genai`: fuzzy evidence finding or text interpretation.
- `code_engine`: deterministic calculations, date math, thresholds, caps, equality/comparison checks.
- `db_query`: local program facts, eligibility code, contractor registration, prior rebate history.
- `external_lookup`: product lists, certification lists, AHRI/NRCan/CPD/ENERGY STAR/NEEA lookups.
- `manual_review`: judgment, missing evidence, or policy/program review.
- `hybrid`: GenAI locates evidence, then code/DB/external/manual review evaluates it.

This matrix intentionally avoids "LLM does everything". The existing schema already supports `source_engine = 'code'` and `source_engine = 'genai'` for located fields and rulechecks.

## Columns

| Column                  | Meaning                                                              |
| ----------------------- | -------------------------------------------------------------------- |
| `source_requirement_id` | Stable local ID for traceability.                                    |
| `source_section`        | Public requirements section.                                         |
| `app_upgrade_type`      | Current app `SubmissionVariant`, or `All`.                           |
| `detected_subtype`      | Finer category inside an upgrade type.                               |
| `requirement_summary`   | Short paraphrase of the public requirement.                          |
| `source_anchor`         | Public source line/section hint for follow-up.                       |
| `evidence_source`       | Invoice, supporting document, DB, external list, or admin review.    |
| `automatable_level`     | How directly the system can check it.                                |
| `evaluation_notes`      | Internal analysis notes; not part of the GenAI output schema.        |
| `v1_rule_action`        | `enforce`, `warn`, `show_unknown`, `manual_only`, or `out_of_scope`. |
| `output_rule_key`       | Stable rule key for persisted rulechecks.                            |
| `notes`                 | Implementation or policy caveats.                                    |

## Multi-Upgrade Invoice Implications

If one uploaded commercial invoice can contain more than one upgrade type, this matrix should be applied at three levels:

- Document-level common rules: invoice date, invoice ID, vendor, customer, total, amount due.
- Upgrade-claim-level common rules: rebate line, eligible cost, amount/cap by claim.
- Upgrade-specific rules: U-factor, R-value, AHRI, Tier 2, amp level, health/safety remediation type, ventilation specs.

Safe v1 assumption:

- One invoice is reviewed as one Windows and doors claim.
- Multi-upgrade invoices are a v2 child-claim model.

## Gate 0 Working Conclusion

The architecture still makes sense if the product is framed as AI-assisted pre-review:

- OCR extracts first-class invoice fields.
- GenAI locates fuzzy/domain evidence.
- Code evaluates deterministic dates, math, thresholds, caps, and DB comparisons.
- DB/external/manual review supplies facts the invoice cannot prove.

The architecture does not make sense if the expectation is "GenAI alone decides full rebate eligibility from the invoice PDF."
